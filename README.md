# Mohsin FutureTech — Online Fashion Store

Production e-commerce site for a Pakistani clothing store, built from
[`docs/proposal.pdf`](docs/proposal.pdf).

**Stack:** Next.js 16 (App Router) · TypeScript · Tailwind CSS 4 ·
Supabase (Postgres, Auth, Storage) · Zod · Vitest · Playwright · Vercel.

> Work is delivered in phases (see the project plan). The old AI-generated
> code is kept in `legacy/` for reference only and will be deleted in Phase 9.

## Project layout

```
src/app/              routes (pages + API route handlers)
src/config/store.ts   brand, contact, delivery & upload defaults (ONE place)
src/app/globals.css   design tokens (colours, fonts, radius) — re-brand here
src/components/ui/    design-system primitives (Button, Badge, Price, Icon, states)
src/components/layout header, mobile menu, footer, WhatsApp button
src/lib/catalog/      catalogue queries (cached 60 s) + Zod row mappers
src/lib/domain.ts     order/payment statuses + workflow (mirrors DB enums)
src/lib/env.ts        Zod-validated environment variables
src/lib/supabase/     browser, server (RLS) and service-role clients
supabase/migrations/  schema, functions, RLS policies, storage (apply in order)
supabase/seed.sql     sample catalogue — GENERATED by scripts/generate-seed.mjs
public/placeholders/  original placeholder images used by the seed
tests/unit/           Vitest unit tests
tests/db/             Vitest database tests (RLS, orders, payments, stock)
tests/e2e/            Playwright end-to-end tests (desktop + mobile)
docs/                 proposal and reference screenshots
```

## Getting started

```bash
npm install
cp .env.example .env.local   # then fill in your Supabase dev project values
npm run dev
```

### Database

Apply every file in `supabase/migrations/` **in order**, then `supabase/seed.sql`
(sample data — skip it for the client's production project):

- Supabase CLI: `supabase link` then `supabase db push`, or
- Dashboard → SQL Editor: paste and run each file in order.

Make yourself an admin after signing up (SQL Editor):

```sql
update public.profiles set role = 'admin' where email = 'you@example.com';
```

## Tests

| Command | What it runs |
|---|---|
| `npm test` | Unit tests (Vitest, jsdom) |
| `npm run db:start` | Starts the local Supabase stack (Postgres, Auth, REST, Storage) in Docker; migrations + seed apply on first start |
| `npm run db:env` | Prints the local Supabase URL and demo keys (copy into `.env.local` for local dev) |
| `npm run test:db` | Database tests: RLS, order placement, payments, stock, concurrency |
| `npm run db:reset` | Re-applies every migration and the seed from scratch |
| `npm run test:e2e` | Playwright on a production build against the local Supabase (desktop + mobile, incl. axe accessibility checks) |
| `npm run lint` / `npm run typecheck` / `npm run build` | Quality gates |

The local stack is the official Supabase CLI (`supabase/config.toml`), so tests
run against the same Postgres 17 / PostgREST / Auth / Storage as hosted
Supabase. E2E tests read its URL and demo keys automatically and never touch a
real project.

## Security model (summary)

- RLS is enabled and forced on every table; table privileges are narrowed too.
- Shoppers read only the active catalogue and store settings.
- Customers read only their own profile, addresses, wishlist, orders and payments.
- Orders and payment evidence are created only through database functions
  (`place_order`, `submit_payment_evidence`) called by validated server routes;
  stock is locked and decremented in the same transaction.
- Admin actions (`review_payment`, `update_order_status`, `adjust_stock`) check
  the admin role in the database and write an audit trail.
- Storage: product images public-read/admin-write; payment receipts private,
  server-uploaded, admin-read; JPG/PNG/WebP up to 5 MB.
